## The setup that worked

Recorded so it does not have to be rediscovered:

```
open localhost:9010 as TDV2200, 80 x 25          <- 25 ROWS. Not 24.
TRACESTART, LOGSTART                             <- before anything else
SENDRAW ESC                                      <- wakes the SINTRAN line
SEND "SYSTEM\r\r"                                <- one send, name + CR + blank password
SEND "set-term-type,,93\r"                       <- SINTRAN accepts it silently
SEND "ped\r"
```

**80 x 25, and this cost the first attempt.** `terminal_open` defaults to 24 rows. PED addresses row
25 — an `ESC[25;1H` followed by its dim-reverse status line — so at 24 rows the "Expand" indicator is
simply not there. Nothing looked broken; a whole row was just missing. The default should come from
the emulator's own recommended size, which `EmulatorFactory` already knows.

**PED's HOME toggles**, and this cost two wrong turns at the keyboard. HOME switches between the
`PED:` command line and the text area, and PED *starts* with the cursor on the command line — so the
first HOME moves you **down into the text**, not up to the command line, and typing `EXIT` there puts
the word in the document. Exit is: HOME (only if you are in the text), `EXIT`, then `N` to the "text
is modified, store it?" prompt.

## M4.2d — answered, the half that could be

**PED's own guide settles what to expect:** "HOME — Move to command line (PED:)".

`SENDKEY HOME` transmitted **GS `0x1D`**, and the cursor moved to **row 0, column 4** — parked
immediately after `PED:`. That is exactly the documented behaviour, so **real PED acts on GS `0x1D`**,
and our reference is right where the other document claimed DLE `0x10`.

**What it does NOT settle**, and why the case stays open: which byte a physical TDV *keyboard* put on
the wire, and the behaviour in *simple ASCII mode* specifically — this was PED's page mode at terminal
type 93. Recorded as answered-in-part rather than passed.

**A near miss worth keeping.** On the first attempt I read the screen mid-paint, saw the cursor at row
0 column 4, and wrote it down as suspicious — an editor's caret on the title line. It was PED parking
the cursor after `PED:`, which is correct. Reading the bytes rather than chasing the screen is what
stopped that becoming a phantom defect.

## M7.1 — the counter was too narrow, then it was not

`UNHANDLED` first reported **"nothing unhandled"** for a whole PED session while the trace showed
`ESC Q` arriving at startup. Both were telling the truth: the counter covered only the ND `ESC "`
graphics modes and the ReGIS command letters, and **did not count escape sequences the PARSER failed
to recognise** — which is exactly where a real host's unknowns turn up.

The counter now covers unrecognised escape and control sequences, unknown mode numbers, and device
control strings. With it, one PED startup gives a work list of **five keys**:

```
mode 62 set x2      mode 30 reset x1      mode 7 reset x1      mode 80 reset x1
DCS L x4            <- "L10".."L40", four payloads dropped in silence until this counted them
```

**Captured deliberately the second time**, rather than read off a trace by hand:
`set-term-type,,93`, `TRACECLEAR`, then `ped`, so the capture holds PED's startup and nothing else.

```
1B 51                          ESC Q
1B 5B 33 30 3B 37 3B 38 30 6C  ESC [ 30;7;80 l
1B 5B 36 32 3B 36 32 68        ESC [ 62;62 h
1B 50 4C 31 30 1B 5C           ESC P L10 ESC \
1B 50 4C 32 30 1B 5C           ESC P L20 ESC \
1B 50 4C 33 30 1B 5C           ESC P L30 ESC \
1B 50 4C 34 30 1B 5C           ESC P L40 ESC \
1B 5B 30 30 31 3B 30 30 31 48  ESC [ 001;001 H
1B 5B 32 4A                    ESC [ 2J
```

Those bytes are now a test rather than a note:
`tests\RetroTerm.Tests\TDV\PedStartupCaptureTests.cs`. Six cases, and the last
asserts the count is **exactly five keys** — so if a later change breaks CUP, ED or the DCS framing,
the list grows and the test goes red naming the newcomer.

**Two things the capture settled that the hand-reading had not:**

- **PED as a TDV gets one more text line.** `Line: 1-21` at terminal type 93, against `Line: 1-20` at
  type 134. That is the 25th row a TDV2200 has and a VT100 does not, being used.
- **PED writes zero-padded parameters** — `ESC [ 001;001 H`, not `ESC [ 1;1 H`. Nothing else in the
  suite had fed the parser a padded parameter. It handles them; there is now a test saying so.

**Mode 62 has a second, independent witness.** A real TDV2200 termcap's `is` string is
`\E[62;36;66l \EQ \E[36;62;62h \E[0m` (the `is` capability in `docs\TermCap.txt`, the primary source;
the expanded `TDV2200 TERMCAP REFERENCE.md` that used to be cited here was retired on 29 September 2026). PED
sends the same three-part ritual with different numbers: an `ESC Q`, a reset list, then a set list.
Mode 62 is in both. **What neither source says is what mode 62 DOES** — the termcap reference marks
these "Function: Unknown", "No evidence currently available", and asks for the TDV2200 Programmer
Reference Manual. So it stays counted, not implemented.

## 132 columns — answered, and it closed Phase 1

`set-term-type,,0` makes SINTRAN prompt for the terminal type and print all eighteen it supports.
**The width is part of the TYPE**: 6 is "DEC VT100 (80 columns)", 134 is "DEC VT100 (132 columns)".
Answering 134 made SINTRAN send `ESC <`, then **`ESC [ ? 3 h` — DECCOLM, 132 columns on** — then
`ESC =`, `ESC ( B`, `ESC ) 0`. PED redrew as `Column: 1-132`.

**No TDV type in the list is 132 columns.** That settles the argument between our own two documents:
the profile comment at `TerminalProfile.cs:85` is right, and the DECCOLM row in
`TDV-COMPREHENSIVE-REFERENCE.md` (retired 29 September 2026) was ours, not Tandberg's. Written up in full in
`docs\PLAN.md`.

## Correction: two findings were mine, not the program's

Both came from believing the trace's `UNKNOWN` label instead of reading the code.

- **`ESC Q` is handled.** `TDV2200Emulator.cs:482` — "exit 2115 compatibility mode". The counter was
  right to stay silent and the trace was wrong to call it unrecognised.
- **`ESC <` is handled too**, as NDVIDEO, the TDV's alpha/graphics toggle.

**The trace's vocabulary is narrower than the emulator's, and its `UNKNOWN` means "the DECODER does
not know this", not "the terminal ignored it".** That is a trap for exactly this kind of work. Use
`UNHANDLED` for "what did the terminal not act on"; use the trace for "what arrived, in what order".

**`ESC <` is also a two-meaning clash**, the same shape as the `ESC c` one already on the standing
list: NDVIDEO on a TDV, enter-ANSI-mode on a DEC terminal. It only came up because SINTRAN believed
it was talking to a VT100 while a TDV2200 was decoding — my doing, not a defect.

## Open: a defect in the trace itself — observed ONCE, not reproduced

The **outgoing** decoder keeps escape-sequence state across time with no flush. A standalone `ESC`
sent to wake the line sat in that state for **fourteen seconds** and then swallowed the next
keystroke: a trace entry reading `ESC S — Unrecognised sequence` where the raw block plainly carried
`53 59 53 54 45 4D 0D 0D`, an ordinary "SYSTEM\r\r".

Nothing wrong reached the host. But **this is the instrument every other case is judged with**, and it
invented an unrecognised sequence out of a normal keypress.

**It did NOT reproduce.** A second session, driven the same way, decoded the same keystrokes as a
plain `"SYSTEM"` with no glued escape at all. So it is real — the first trace records it, with the raw
block proving the wire was clean — but intermittent, and what makes the difference is not yet known.
Recorded as observed-once rather than as a confirmed defect, because asserting a cause would be
exactly the guessing this pass exists to replace.

**This is the one item here that is still live.** It is carried on the run sheet as a watch item: if
it happens again during any session, capture the trace and the raw block together and it becomes a
test.

---

## The honest limit on all of it

The CPU is emulated by RetroCore. What SINTRAN *sends* is real software behaving normally. What a
physical TDV did when those bytes arrived is not something these sessions can tell us, and it is not
written down as though it were.

# Later sessions

## 25 August 2026 — a VT340 cannot enter Tektronix mode. DECTEK is not implemented

**Confirmed defect. Found by accident, during session 1, because Ronny refused to let it be parked.**

**How it surfaced.** The test server's Tektronix entry was run against a **VT340** session while
setting up case M6.5. Instead of drawing a box and a grid, the terminal printed the coordinate bytes
as visible text — `!r!R!r>J6z>J6z!R!r...` straight across the screen. Screenshot taken at the time.

**My first reaction was wrong twice over.** I said it "may be the test's fault" and that I would
"check it properly rather than guess, but not now". Both halves were bad: it was not the test's
fault, and deferring a defect that is failing on screen in front of you is how a defect stops being
looked at. It took one grep to settle.

**What the grep says.** Across the whole of `src\RetroTerm.Core\Terminal\Emulators\`:

 - There is **no handler for private mode 38** (`ESC[?38h`, DECTEK). The only matches for "38" in
   that tree are a Tektronix character-size row count and an unrelated buffer constant.
 - `GS` (`0x1D`) is handled in exactly **three** places: TDV2115 cursor-home, twice, and
   `TektronixVectorDecoder.cs:137`.
 - `TerminalEmulatorBase` — which every VT emulator derives from — handles neither.

**So the behaviour is exactly what the code says it should be.** Nothing listens for the sequence
that asks a VT to become a 4014, so the vector bytes fall through to the text path and get printed.
The emulator is not misbehaving; the feature is absent.

**What DOES work, and why this was not noticed.** `Tek4014Emulator` is a **separate terminal type**
picked from the emulation menu, and it is complete — every M5 sheet in the manual pass is drawn with
it. Tektronix support in this program has only ever been reachable by choosing Tektronix as the
terminal, never by a host asking a VT for it.

**Why it is a real gap and not a wrong expectation.** A real VT330/VT340 has Tektronix 4010/4014
emulation built in, entered with DECTEK. A host that sends `ESC[?38h` to a VT340 and then plots is
doing the ordinary, documented thing. We answer it by printing rubbish.

**Not fixed today, by decision.** Ronny chose: write it up now, finish the six manual cases, then
implement it with tests. Recorded here so it cannot quietly become folklore.

**What a fix has to cover, when it happens:**

 - `ESC[?38h` enters Tektronix mode, `ESC[?38l` leaves it. Both need the UNHANDLED counter to stop
   reporting them.
 - The VT emulators need to route bytes to the existing `TektronixVectorDecoder` while in that mode
   rather than duplicating it — the decoder is already right, and this is the
   one-behaviour-one-place rule.
 - Leaving the mode must put the text cursor somewhere defensible. The gnuplot label cascade came
   from exactly this, and it is written up under the rendered-image section of CLAUDE.md.

## 25 August 2026 — a blank screen during M6.5 that did NOT reproduce

**Not a confirmed defect. Recorded because it was seen, and because the reproduction attempt is
worth keeping.**

Ronny pressed the key that starts graphics input mode and reported the screen went blank. Reading
the text buffer over the wire at the same moment showed **the text was all still there** — round one
had finished and round two had started. So the characters were in the buffer and something was
hiding them, which is a rendering question, not an emulation one.

**The reproduction attempt.** `RegisGraphicsInputTextSurvivesTests.cs` feeds the exact bytes that
menu entry sends through the real `TerminalCanvas` and captures the pixels. Both tests **pass**, and
`regis-input-text-after.png` shows the text, the drawing and the white crosshair all present and
correct. So the ReGIS payload on its own does not blank anything.

**What was different about the live session, and not ruled out:** that tab had already had a
screenful of Tektronix garbage printed through it (see above), and a stray keystroke sent from the
MCP side had desynchronised round one from the host. Either could be the cause. Neither is proven,
and no cause is claimed here.

**The test earns its place regardless** — nothing else in the suite renders the whole control and
asks whether the text is still readable after a drawing arrives. Every other graphics-input test
looks at emulator state or at the plane.

### Why no test caught it, and what would have

**Nothing failed because nothing asked.** Every Tektronix test in the suite constructs a
`Tek4014Emulator` directly and drives it. Not one sends `ESC[?38h` to a VT and looks at the result.
A suite catches what somebody thought to write down; nobody thought to write that down.

**The machine that should have caught it already exists and was never pointed at this.** The
`UNHANDLED` counter records any sequence the emulator does not recognise, keyed WITH the mode number
for modes. `ESC[?38h` sent to a VT340 would have been counted the very first time. It has never been
sent to a VT340 by anything.

**Every DEC private mode the emulator handles today**, read off the switch in
`TerminalEmulatorBase.SetDecPrivateMode` on 25 August 2026 rather than remembered:

    1  2  3  5  6  7  9  12  18  19  25  43  44  45  47  69  80
    1000  1002  1003  1004  1006  1047  1048  1049  2004

That is the complete list. Anything not in it is unhandled, DECTEK among them.

**The test that would have caught this, and should exist:** walk every private mode the VT330/VT340
manual documents, send each one to a VT340, and assert the UNHANDLED counter stays empty. That turns
"we forgot" into a build failure. It needs the authoritative mode list, which is in
`spec\DEC\EK-VT3XX-GP-002_VT330_VT340_Graphics_Programming_May88.pdf` and in
the VT420 reference beside it — **it must be read out of those, not recalled**, or the test simply
encodes the same blind spot in a new place.

**This is the real work item.** Implementing DECTEK fixes one mode. The sweep finds the rest.

### The counter itself had a hole — fixed 25 August 2026

**This turned out to be bigger than the missing mode.** Chasing why the UNHANDLED counter never
reported DECTEK led to the end of `TerminalEmulatorBase.SetDecPrivateMode`:

```
default:
    // Unknown mode
    break;
```

**Every unknown DEC private mode was silently discarded.** `SetAnsiMode` had counted its unknowns
since the counter was built — its comment even explains why a mode must be counted WITH its number,
because "for a mode the number IS the thing". The private side never did. So the mechanism whose
whole purpose is to make a missing feature announce itself was blind to the entire numbering space
where DEC put nearly everything interesting: DECTEK, DECNRCM, DECNKM, DECBKM, smooth scroll,
auto-repeat.

**The fix** counts them, keyed `"private mode N set"` / `"private mode N reset"`. The word *private*
is not decoration: ANSI mode 4 is IRM and private mode 4 is DECSCLM, so sharing a key would add two
unrelated things together and report a total that means nothing.

**Red before green, and it happened by accident, which is the best kind.** The three new tests in
`DecPrivateModeCoverageTests` were written expecting the counter to work. All three failed. That
failure is what exposed the hole — the test found something nobody was looking for, rather than
confirming something already known.

**The full sweep now exists:** `tests\RetroTerm.Tests\Terminal\DecPrivateModeCoverageTests.cs` walks
every private mode the DECSET table attributes to a DEC terminal, and fails the build if one is
neither handled nor on a written list of gaps with a reason. The gap list is deliberately a list
rather than a bare assertion, so that implementing a mode produces the message *"take it off the
list"* instead of a red test that looks like a regression.

**Suite after the change:** 6319 passed, 41 skipped, 0 failed, plus 123 Kermit.

## 25 August 2026 — the TDV key registry checked end to end against a real ND host

**Not our measurement.** Run by the session working on VTM (the ND terminal-independence layer)
against a real ND-100, and reported across. Recorded here because it answers a question this run
sheet had listed as open, and because nothing in this repo could have answered it.

**What was measured.** A key name goes into RetroTerm's `SENDKEY`, out over the wire, through VTM's
decoder, and lands as a number inside a PLANC program that prints it. The same key was then sent as
raw bytes with `SENDRAW`, to see whether the two routes agree.

| Key | Through SENDKEY | Through SENDRAW | VTM's code |
|---|---|---|---|
| HJELP | grid G53 | `ESC[46_` | 191 |
| ANGRE | — | `ESC[30_` | 216 |
| F3 | grid F53 | `ESC[55_` | 149 |

**They agree exactly.** Thirteen observations for six keys plus markers, and the count was exact — so
nothing was dropped or merged along the way.

**What that does and does not settle.** It settles that **our registry produces what a real host
accepts**: legend to grid position to bytes to decoded key code, with no disagreement. That is the
first end-to-end check the TDV keyboard has ever had, and it is the half of case 11 that can be
answered without a physical TDV. It does **not** settle what an original Tandberg keyboard put on
the wire — that still needs the hardware, and stays on the never-unless-something-turns-up list.

**Two things that came back the other way, and both were ours to answer:**

 - **`ESC[42_` makes VTM swallow the next byte.** Correct on both sides. That is grid **G51, legend
   FUNK** — a function-SHIFT prefix. VTM is waiting for the key FUNK modifies. Worth knowing when
   writing a key loop: a stray FUNK makes the next keystroke vanish, and that is the keyboard's
   design rather than a fault.
 - **`ESC O P` and `ESC O Q` decoded inconsistently.** Both are sequences this emulator really emits
   (`KeyboardMapper.cs:391`, VK_F1..VK_F4), both well formed, and DECKPAM does not touch the
   uppercase forms — our application-keypad mapping only covers `ESC O p` through `ESC O y` and the
   operators. So the asymmetry is in VTM's decoder, not in what reached it. Left open on their side
   rather than written down as understood, which is the right call.
   **A caveat worth carrying:** on real DEC hardware those four bytes are the *keypad's* PF1–PF4,
   not the top-row function keys. We map them to F1–F4, as every modern emulator does, so one
   sequence serves two physically different keys.

## 25 August 2026 — opening a connection underneath a modal dialog

**The mechanism, found rather than guessed.** Manage Connections is shown with `ShowDialog(this)` —
a true modal, so the main window is **disabled** while it is up. The MCP open path then called
`CreateTab` on that disabled window, and a `TerminalCanvas` takes the focus the moment it is attached
to the visual tree. Ronny was in that dialog when it happened, and the interface stopped responding.

**MCP now refuses**, naming the window that is in the way, rather than queueing. The caller learns
why, and the person at the keyboard is not interrupted by something they never asked for.

`MainWindow.OpenModalDialogTitle()` asks the window for its own `OwnedWindows`. The first attempt
asked `Application.Current.ApplicationLifetime` for its window list and returned null every time
under test — the headless lifetime is not the classic desktop one — so the guard would have been dead
in the only place it could ever be proven. Four of the five tests caught it.

**What is NOT proven:** that a focus grab inside a disabled window is what broke the interface. No
headless test can answer that. The fix is to stay out of the situation rather than to survive it,
which is the right shape regardless of which detail did the damage.

**A correction first.** The claim "nothing anywhere" was wrong. There WAS a log,

## 25 August 2026 — the trace decoder's stale escape, explained and fixed

The watch item recorded above under *Open: a defect in the trace itself* is closed. It was not
intermittent in the way it looked; it was **deterministic given a block boundary**, and the second
session simply did not land one in the same place.

**The mechanism, read out of the code rather than guessed.** `WireScanner.Feed` ends by flushing a
trailing run of printable text so a single echoed keystroke shows up at once. It never flushed a
half-finished SEQUENCE. So a block containing only `ESC` left the scanner in its escape state, and
the first byte of the next block — the `S` of `SYSTEM` — was taken as that escape's final byte.
`StepEscape` sees a byte that is not `[`, `]`, `P` and not an intermediate, and hands it to the
decoder as a complete two-byte sequence. That is exactly the `ESC S — Unrecognised sequence` in the
trace, and exactly why the `S` went missing from the text beside it.

**Why the state could not simply be dropped at each block.** A real sequence does arrive split
across two network reads; the sample log this scanner was written from shows `1B 5B` ending one
packet and `36 3B 33 48` starting the next. Throwing the state away every time would break that,
which is a worse trade than the defect.

**What separates the two cases is time, and nothing else in the bytes.** A split packet continues in
single-digit milliseconds. The observed pause was fourteen seconds. A one-second limit is a hundred
times longer than the case being protected and fourteen times shorter than the case observed, so
nothing has to be finely judged for it to be right.

The half-finished sequence is now **emitted as itself**, marked not known, saying how long it
waited. Discarding it silently would be a different kind of lie — the byte was on the wire, and a
trace that quietly loses bytes cannot be used as evidence about the ones it kept.

Six tests in `WireScannerStaleEscapeTests`, with an injected clock so the gap is stated rather than
waited for. Three of them go red with the fix disabled, including the one built from the observed
bytes.

## 25 August 2026 — a TDV2200 mode sequence that no manual describes

**Found while checking a plan entry, and the plan entry was wrong.** It said the TDV2200 "claims
Tektronix and does not have it". The second half is false: `TDV2200Emulator.ConsumeGraphicsByte`
offers every Ground-state byte to `NorskDataGraphicsModule.ConsumeVectorByte`, unconditionally, so
the terminal draws Tektronix vectors perfectly well. The real defect is the other way round.

**`CSI n greater-than` has no source.** Modes 0 and 1 were read as enabling and disabling a graphics
extension, and 2 and 3 as entering and leaving Tektronix mode. Searched on 25 August 2026:
`spec\Tektronix\nd-graphic-terminal-analysis.md`, `spec\TDV1200\tdv_1200_graphics_library_extended.md`
and `docs\TDV-COMPREHENSIVE-REFERENCE.md` (since retired). **None of the three names the sequence at all.** It is our
own invention, the same way the `?3 DECCOLM` row in the TDV reference turned out to be.

**And the numbers look borrowed from a different sequence family.** The ND analysis does have a
mode 2 and a mode 3 — under `ESC "`, where 2 is *set write mode* (replace, OR, XOR, complement) and
3 is *set line style*. Neither has anything to do with Tektronix. The likeliest story is that those
numbers were carried across to the wrong introducer.

**What the invention actually cost.** Both flags gated nothing except two diagnostic strings, and
those strings then lied in the useful direction: the terminal reported no Tektronix and no graphics
until an imaginary sequence arrived, while drawing vectors the whole time. Nothing in `src` reads
those strings, so the damage was confined to tests — but **nine test assertions had been written
from the code and were pinning the invention in place**, which is what would have made this hard to
find later.

Now: both abilities are reported unconditionally because both are unconditionally true, and the
sequence goes to the unrecognised counter with its parameter, so a real ND host can supply the
meaning instead of us guessing a second time.

## The monitor move does NOT leave content at the old size — closed 31 August 2026

Reported 29 August 2026 on Ronny's screen: dragging the RetroTerm window to another monitor grew
the window to about 1293 wide while the terminal pane went on painting in the old 800 by 640 box,
with the rest of the window black. No resize, no repaint.

**Retried by Ronny on 31 August 2026 and it did not happen — the text area resized correctly.**

The build he retried on matters, because that is the whole reason the item stayed open. It was the
running `publish\RetroTerm.Desktop.exe`, PID 34452, built 10:46 on 31 August from a CLEAN tree at
commit `2ad56fe`, confirmed by `git diff HEAD -- src tests` coming back empty. Measured rather than
assumed: the exe's SHA-256 is `16C6A2D3F786D5B58F72E64394290CAAED1F84E9B84169C1BE98AD77C66B4E6B`,
which is NOT `1.0.26.2-2`'s `B1A5E0ED0EB378DC13EEBBE557986F9BF0901254AB73C47C2F2D0D462B39560F` even
though the two files are the same size to the byte. Same size, different build. Checking the hash
rather than the size is the only reason we know which build the verdict belongs to.

**What this confirms is the diagnosis already reached on 29 August**, when three causes were ruled
out rather than found:

 - the plain window-resize path works. `WindowResizeReachesTheCanvasTests` drives a real shown
   Window, grows it and shrinks it, and the canvas follows and asks for the new grid both ways.
 - cell metrics are computed once in the renderer's constructor and never again, which looked like a
   stale-metrics cause until it did not: they are in logical units, and scaling is applied at draw
   time.
 - nothing in the desktop layer observes `RenderScaling` or a scaling change at all.

What was left standing was the BUILD he saw it on, which could not be published at all that day —
a day old and made from a dirty tree. A clean-tree build does not show it. That is the cause.

**The lesson is the one from 29 August, and it has now cost twice:** a defect reported against a
build that could not be published is a defect report about an unknown binary. Publish first, confirm
which build is running, and only then judge. See the CLAUDE.md section "A GREEN BUILD DOES NOT MEAN
THE APP CAN BE SHIPPED".
