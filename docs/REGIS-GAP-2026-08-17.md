# What ReGIS still cannot do — read against DEC's own manual

**Full path:** `docs\REGIS-GAP-2026-08-17.md`
**Date:** 2026-08-17 (rewritten the same day, see below)
**Source:** `spec\DEC\EK-VT3XX-GP-002_VT330_VT340_Graphics_Programming_May88.pdf` — "VT330/VT340
Programmer Reference Manual; Volume 2: Graphics Programming, 2nd Edition", 305 pages.
**Covers:** `src\RetroTerm.Core\Terminal\Graphics\RegisDecoder.cs`

## Why this was rewritten

The first version of this file was written from `regis/regis-commands.txt` in hackerb9's vt340test
collection, a third-party retyping of Table 1-1, because the manual was not held. It now is. The
gaps named then are still gaps, but the evidence below comes from the manual's own chapters.

**A note on reading this PDF.** It is a scan run through OCR. The prose comes out clean; the
TABLES — including Table 1-1 itself and every per-chapter command summary — come out as garbage,
because they are images the OCR could not lay out. So the evidence here is taken from the chapter
BODIES, which state the same rules in sentences. Anyone re-checking a table should render the page
as an image rather than trust `pdftotext`.

## The ten commands, from the manual's own chapter list

"ReGIS has 10 basic commands (Table 1-1)." Each has its own chapter, which is a firmer source than
the table:

| Letter | Chapter | What it does | Ours |
|--------|---------|--------------|------|
| `S` | 2  Screen Control  | erase, coordinate axes, **colour map** | Erase and colour map |
| `W` | 3  Write Control   | colour index, shading, negation        | Yes |
| `P` | 4  Position        | move without drawing                   | Yes |
| `V` | 5  Vector          | straight lines                         | Yes |
| `C` | 6  Curve           | circles and arcs                       | Yes |
| `T` | 7  Text            | draw text into the graphics plane      | **Yes**, 2026-08-18 |
| `L` | 8  Load            | define alternate text characters       | **Yes**, 2026-08-18 |
| `@` | 9  Macrographs     | store a command string and replay it   | **Yes, as of 2026-08-17** |
| `R` | 10 Report          | report position and errors to the host | **Yes**, 2026-08-18 |
| `F` | 11 Polygon Fill    | fill a closed figure                   | **Yes, as of 2026-08-17** |

All ten are built as of 2026-08-18. While a command was in the "No" group it was counted in
`RegisDecoder.UnhandledCommands` and its bracket, parenthesis and quoted-string groups were
skipped, so an unsupported command cost the drawing that shape and nothing else; the options that
are still deliberately not built (listed under `T` and `R` below) are counted the same way.

## The defect this reading found — `@` was not merely missing

The skip-and-count rule above has one requirement: the command must HAVE brackets to skip. The
macrograph does not. `@` is not a letter, so it fell through to the "advance one character" path,
and the consequences ran in both directions at once:

- `@:A ...body... @;` — the body was **drawn immediately**, which is the exact opposite of the
  manual's "The VT300 does not draw macrographs when you define them."
- `@A` — an invocation **drew nothing**, because nothing had been stored.
- `@:A` — the call letter `A` was counted as a phantom unhandled command.

So it is now implemented rather than skipped, which is the smaller job of the two: a macrograph
body is made of the S, P, V, C and W commands the decoder already runs. From the chapter:

- `@:letter definition @;` defines. `@letter` invokes. `@.` clears all 26. An empty definition
  clears one slot.
- 26 slots, call letters case insensitive, "at least 10,000 bytes" of storage.
- Nesting up to 16 levels, and "a macrograph cannot call itself". Both are enforced — the depth by
  a counter, the self-call by a busy flag. Without the flag the self-calling case does not fail a
  test, it never returns, which is why it is a rule and not a hope.
- "ReGIS does not recognize any commands in a quoted text string", so the search for the `@;`
  terminator steps over quoted text. A `T'@;'` inside a definition is text.
- Definitions cannot nest, so the first terminator outside quotes is the right one.

Replay allocates nothing: a definition is stored once as a string and replayed through
`AsSpan()`. `tests\RetroTerm.Tests\Terminal\Graphics\RegisMacrographTests.cs` has eleven tests;
four of them go red with the `@` case removed.

## The colour map, from the manual rather than from a fixture

`S(M`_n_`(H`_h_`L`_l_`S`_s_`))` sets colour map entry _n_, and `sixeltests/cat-original.six` opens
with four of them before a Sixel image that defines no colour of its own. Both halves of that are
now done: `S(M...)` is implemented, and `GraphicsColorMap` is the ONE map both decoders write to,
because a VT340 has one map of sixteen locations and both graphics languages reach it.

The default map is Table 2-3 from the manual. Both palettes it replaced were wrong, differently:
the Sixel one made entries 9 to 14 *brighter* than 1 to 6 where the footnote says they are less
saturated, and the ReGIS one used fully saturated primaries throughout.

The picture that proved it: `tests\RetroTerm.Tests\Avalonia\images\rendered\vt340-sixel-cat-original.png`
against `tests\RetroTerm.Tests\Conformance\vt340test\cat-original.png`.

## Polygon Fill — done 2026-08-17

Chapter 11 made this much smaller than it first looked. **F defines no geometry of its own.**

> "The polygon fill command accepts all vector command options and arguments."
> "The polygon fill command accepts all curve command options and arguments."
> "The polygon fill command accepts all position command options and arguments."
> "The polygon fill command accepts all write command options and arguments."

So `F(...)` re-runs V, C, P and W — all implemented — with the stroking replaced by vertex
collection and one fill at the end. The rules the chapter states:

- At least 3 distinct vertices or nothing is drawn; at most 256, the rest ignored; two consecutive
  vertices on the same pixel count as one.
- "Each argument for the vector option creates one vertex. Each argument for the curve option can
  create more than one vertex."
- An unclosed figure, or intersecting closed figures, are explicitly "unpredictable" — so there is
  no correct answer to match, and any sane result passes.
- Fill uses the current foreground colour.
- "ReGIS saves the cursor position at the beginning of any polygon fill command. The cursor returns
  to this position at the end of the command (whether or not any drawing takes place)."
- Only the LAST `W` option in the command affects the image, "because ReGIS does not draw the image
  until the end of the polygon fill command" — the one exception being PV multiplication.
- "In some cases, the outline of the filled polygon may not line up exactly with the vectors that
  connect the same vertices. You should draw a border after the filled area." Real hardware did not
  match its own outline, so an exact-pixel test against a capture would be wrong to write.

So it took one new surface method — an even-odd scanline `FillPolygon` beside `DrawLine` and
`FillRectangle` — and **no new parsing at all**. The F body is run by the ordinary decoder with a
flag set; V and C add vertices instead of putting ink down, and one fill happens at the end.
Every rule above is implemented and cited in the source. `F(@X)` — the manual's own idiom for
giving a filled shape a contrasting outline — works, because macrographs went in first.

A filled circle is a 64-sided polygon: the fill takes vertices and a circle has none. Sixty-four
keeps the chord error under a pixel out to radius 800, the whole width of the ReGIS space, and
stays inside the 256-vertex ceiling.

Tests: `tests\RetroTerm.Tests\Terminal\Graphics\FillPolygonTests.cs` (9, surface level),
`RegisPolygonFillTests.cs` (12, decoder level — 8 go red with the `F` case removed), and a rendered
PNG at `tests\RetroTerm.Tests\Avalonia\images\rendered\regis-polygon-fill.png` drawing Figures 11-1
and 11-2. **Looking at that PNG is how the border alignment and the smoothness of the 64-gon were
judged**; no assertion could have told me the circle looked round.

**One thing learned about the test helpers.** `RenderedScreenshot.CellHasInk` cannot see a solid
fill. It counts pixels differing from the cell's own dominant colour, so it measures CONTRAST
inside a cell — a cell wholly inside a filled shape is uniform and reads as blank. For fills the
right helper is `DominantColorInCell`, which asks what colour the cell actually came out.

## The last three commands - all built 2026-08-18, with what each took

### `T` — Text — DONE 2026-08-18

Chapter 7 lists ten options. Seven are implemented: character set (`A`), the standard sizes and the
display cell (`S`), the unit cell (`U`), height multiplier (`H`), size multiplier (`M`), string tilt
(`D`) and italics (`I`). Strings work in either quote, with the doubled-quote rule and the comma
join, and the four control characters ReGIS recognises inside a string — CR back to the column the
command started at, LF down one display cell, BS and HT one character position each way.

**Three are deliberately not built**, and each is counted rather than pretended: PV spacing
(subscripts and superscripts), temporary text control, and temporary write control. Pointed at a
real host, `UnhandledCommands` says whether any program actually uses them.

**The sizes are the manual's; the shapes are not.** Table 7-3 is transcribed into `RegisTextState`
from the printed page — the OCR renders every table in this manual as noise — and S0 and S1 are
written out because they do not follow the `[9n, 15n]` pattern the rest of the table does. The
GLYPHS are the TDV2200 character ROM, used as a stand-in: the chapter prints six example characters
and no font, so the alternative was ninety-six glyphs invented here. Replacing `BuiltInGlyph` with
DEC's own shapes is a one-method change.

**One thing that only the picture could show.** The ROM cell is fourteen rows and ReGIS stores ten,
and quantising the glyph to ten rows before scaling it dropped whichever rows fell between the
samples — for this ROM, the middle bar of an `e` and the dot of an `i`. The first sample sheet read
"Thc quick brown fox" and "S1zcs from tablc 7-3" while all twenty-one assertions passed. Built-in
glyphs are now sampled straight from the ROM at whatever height they are drawn at, and only a
LOADED cell goes through ten rows, because a loaded cell really is eight by ten. At S0 — a
ten-pixel cell — the squeeze still costs detail that DEC's own 8x10 glyphs would have kept, and the
sample sheet shows it.

`tests\RetroTerm.Tests\Avalonia\images\rendered\regis-text-sample.png` is the picture to judge:
five sizes, the height multiplier, italics, two tilted strings and a loaded checkerboard.

### `L` — Load — DONE 2026-08-18, with `T`

All three options from chapter 8: `L(A1..3)` selects the set to load into, `L(A'name')` names it for
the report command, and `L"c"` followed by hex pairs loads one cell — two hex digits per row, top
row first, the first digit being the left four pixels. The manual's odd-digit rule is honoured
("ReGIS assumes the first hex value is 0"), so a single digit fills the right-hand four pixels.

Set 0 cannot be loaded, which is the manual's rule and is enforced rather than assumed. A set that
was never loaded draws NOTHING rather than falling back to ASCII: a host that selected an empty set
and silently got the built-in glyphs would never find out.

### `R` — Report — BUILT 2026-08-18, and ReGIS is now ten of ten

Chapter 10 reports cursor position, macrograph contents, macrograph storage status, character set,
error condition and input mode, and enters graphics input mode for a mouse or tablet. Every report
ends with a CR.

Five of the six are built and answer with the exact bytes the chapter specifies. The decoder
collects what it owes rather than raising an event — it owns no connection — and the emulator sends
it, a path `TheReportReachesTheHostThroughTheEmulator` covers by reading the bytes off the wire.

What is deliberately left:

 - `R(E)` always answers `0,0`. Nothing flags parse errors yet, so that is a truthful report of
   what this decoder knows. It is still SENT, because a host that asks and hears nothing waits
   forever. Table 10-1's error codes are not implemented.
 - Graphics input mode is not a report and needs a pointing device. Still counted.

The macrograph total is 10,000 bytes, from "The VT300 can store at least 10,000 bytes of macrograph
data" — the only figure the manual gives.

## Fixtures that judge the work - FETCHED 2026-08-18, and one claim below was wrong

`tools\fetch-conformance-corpora.ps1` now fetches the ReGIS half too, into
`tests\RetroTerm.Tests\Conformance\vt340regis\`. Nineteen files, CC0, not committed.

**`hersheydemo.regis` does not exercise the text command at all.** This document said it was the
fixture that would judge `T` hard. It is not: opened, it contains **no `T` command and no text
option anywhere**. The Hershey fonts are drawn as VECTORS - 44 KB of `P` and `V` with thousands of
relative moves - so what it exercises hard is the vector command, which it does, and it renders as
`regis-corpus-hersheydemo.png`. The corpus ships no reference capture for it, so whether its
arrangement is right cannot be settled here.

**`registest.sh` is the fixture that judges `T`**, and it comes with four hardware captures -
`registest-grid.png`, `-checkerboard.png`, `-bitplane.png` and `-raf.png`. It uses the text command
eight times and every one of them through the **temporary text control**: `T(B D180 S1 W(I1V))`
then `T(E)`. That option was on the not-built list until this fixture showed it is not optional -
without it the tilt of one label leaks into the next and the labels walk off the screen. It is
built now, together with skipping the temporary WRITE control's own parenthesised group, which
would otherwise have been read as text options and taken an intensity for a cell size.

`resetpalette.regis` is 364 bytes and is the smallest thing that exercises `S(M...)`. It draws
nothing at all, which is what it is for, and the corpus test names it rather than weakening the
"something was drawn" check for every other file.

The two `.sh` fixtures are shell scripts rather than plain ReGIS, so running them end to end needs
a host. The two plain `.regis` files are rendered by the suite as `regis-corpus-*.png`.
## What the grid capture settled, and what it did not - 2026-08-18

`registest.sh grid` is now run by the fetch script and its output drawn beside the capture from the
real VT340, as `compare-registest-grid.png`. The grid, the spacing and the diagonal labels line up.
Four differences came out of it, measured rather than eyeballed.

**Fixed: the default character cell was S0 and should be S1.** Table 7-4 gives the S option a
default of 1, with a footnote saying the defaults are "based on standard S1 character cell" and a
display cell of [9,20]. Every label was drawn at half height until this was corrected. Two tests
moved with it, and each says why.

**Fixed: a number between `T` and its string dropped the whole string.** The script writes
`T22' 0,479 '` and `T4(B D270 S1)`. Nothing in chapter 7 gives a bare number a meaning after `T`
and table 7-4 lists no such option - but the capture shows both labels drawn, so the hardware skips
the digits and carries on. This parser used to abandon the command at the digit, losing the string.

**Open: text at the bottom edge.** The hardware draws the two bottom labels in screen rows 460 to
478 - ABOVE the cursor position at y=479. We draw below the cursor, as chapter 7 says to ("the
upper-left pixel of the 8 x 10 cell is at the cursor position", and a character in the normal
orientation "appears below and to the right of the cursor"), so those labels fall off the plane and
are clipped. Either the VT340 clamps text that would not fit, or the `T22` form positions
differently. The manual does not say, and guessing would put a rule in the decoder that no document
supports.

**Open, and the larger one: line patterns are not implemented.** The script sets `W(P10(M2))` and
`W(P1(M10))`, which give lines a repeating on-off pattern. Measured on the bottom rule of the grid:
the hardware lights **400** pixels of 800 and we light **800**. Every line in that picture is solid
where the hardware's is dashed. `W(P...)` is the next piece of ReGIS worth building, and it now has
a hardware capture to be judged against.
