# Tektronix 4010/4014 mode — read against DEC's own chapter

**Full path:** `docs\TEKTRONIX-4014-GAP-2026-08-17.md`
**Date:** 2026-08-17
**Source:** `spec\DEC\EK-VT3XX-GP-002_VT330_VT340_Graphics_Programming_May88.pdf`, the "4010/4014
Mode" chapter (printed pages 205 to 240).
**Covers:** `src\RetroTerm.Core\Terminal\Emulators\Tektronix\Tek4014Emulator.cs` and
`src\RetroTerm.Core\Terminal\Graphics\TektronixVectorDecoder.cs`.

## Why this replaces the plan's P3.1

An August plan, since retired, proposed reading `vttest`'s `tek4014.c` and hand-writing its byte
streams, because it was "the only Tektronix 4014 test material found anywhere". That was true when
it was written. It is not now: the VT330/VT340 Graphics Programming manual has a whole chapter on
4010/4014 mode, with every sequence printed beside its character-cell codes.

A manual beats a test program twice over here. It says what the sequences MEAN rather than what one
program happens to exercise, and it removes the licence question entirely — the standing rule on
this project is that outside code is a specification to read, never something to port, and there is
now no reason to go near `tek4014.c` at all.

## What is already right

Worth stating, because it is the subtle part and it was got right before this chapter was held:

**ESC-prefixed control codes are told apart from their bare selves.** `Tek4014Emulator.HandleExecute`
tests `Parser.State == ParserState.Escape`, so a bare FF is a form feed and `ESC FF` erases the
tube. The same distinction carries `ESC ENQ` (report status and beam position) and `ESC SUB` (raise
the crosshair and arm GIN). The manual confirms all three.

The coordinate stream — GS, FS, RS, US, the high/low X and Y five-bit groups, and CAN leaving graph
mode — is in `TektronixVectorDecoder` and matches.

## What is missing

### 1. `ESC ETB` — print a hard copy of the bitmap — DONE 2026-08-17

    ESC  ETB
    1/11 1/7

"This sequence prints a hard copy of the terminal's bitmap by using the sixel protocol (Chapter 16).
The sequence also clears the bypass condition. The sequence only works when a printer is connected
to the terminal's printer port."

**This is the same feature as the printing design**, arriving from a third direction. See
`docs\PRINTING-SIXEL-TO-PDF-DESIGN-2026-08-17.md`: the terminal re-encodes its own bitmap as sixel
and sends it out the printer port. `ESC ETB` is Tektronix mode's way of asking for it, alongside
media copy and the ReGIS hardcopy command. All three reach one sink.

**Done.** It was held back on purpose until there was a sink to reach, and now there is:
`PrintGraphics` on the base class, `SixelEncoder` doing the re-encoding. All three clauses of the
manual's sentence are honoured — it prints, it clears the bypass condition, and with no printer
attached it does nothing at all except clear the bypass. That last split matters: a host with no
printer that used ETB to get talking to us again must not be left ignored.

### 2. `ESC CAN` — set the bypass condition — DONE 2026-08-17

    ESC  CAN
    1/11 1/8

"In the bypass condition, the VT300 ignores any data received from the host."

Implemented, and cleared by selecting alpha mode and by `ESC ETB`. Note this is NOT the bare CAN the
vector decoder already handles — that one leaves graph mode, which is a different thing entirely.

One interpretation is marked as one in the source: the manual's "ignores any data received from the
host" cannot be literal, because both clearing sequences are themselves data from the host. So
displayable data is dropped and escape sequences keep running.

### 3. Character size — DONE 2026-08-17

Aligned mode:

    ESC 8   35 lines of 74 characters   (default)
    ESC 9   38 lines of 81 characters
    ESC :   58 lines of 121 characters
    ESC ;   64 lines of 133 characters

Enlarged mode: the same four sequences select 24 lines of 69, and 47 lines of 125.

`ESC 0` through `ESC 3` are aliases, and the manual says: "Digital does not recommend using ESC 0,
ESC 1, ESC 2, and ESC 3. These sequences are not standard Tektronix sequences, and may not be
supported in future terminals."

All eight are implemented. The four Digital discourages are honoured anyway: discouraged is not the
same as absent, and the manual prints what each of them does.

What a real tube does that this cannot: a storage tube keeps what is already drawn, so changing the
character size changes the cell for text written AFTERWARDS and leaves the glass alone - one screen
can carry two sizes at once. This buffer has one cell size for the whole grid, so existing text is
re-laid out instead of staying put. In practice a host sends the size right after an erase.

It also moved the fuzz test's goalposts, correctly. `EscapeParserFuzzTests` asserted that "the
screen must not resize itself... nothing in these inputs asks for it", which stopped being true the
moment a single escape could change the grid - random bytes hit `ESC 8` and friends immediately.
The invariant now says what is actually true for a 4014: any size it lands on is either the size it
started at or one of the four the manual gives. The assertion that matters - buffer and emulator
agreeing, cursor inside the buffer - is unchanged and now runs against the live size.

### 4. Vector patterns — DONE 2026-08-17

    ESC `   solid        ESC d   long dash
    ESC a   dotted       ESC e   solid
    ESC b   dot-dash     ESC f   solid
    ESC c   short dash   ESC g   solid

Implemented, and it needed the surface change first: `IGraphicsSurface.DrawLine` took a colour and
nothing else, so there was nowhere to put a dash pattern. It now carries a `LinePattern` and a
`ref int phase`.

**The phase is the part worth knowing about.** A dashed polyline is ONE dashed line, not a run of
separately dashed segments. Restarting the pattern at every vertex would put a dash at the start of
each one, so a curve sent as many short vectors would come out solid everywhere. The phase is
carried through the corners and reset when the beam lifts, which is what a plotter does.

**The bit patterns are chosen, and marked as chosen.** The manual names the five patterns and does
not print their dash lengths, so the sixteen-bit masks in `LinePatternMask` are this emulator's
reading of those names. They are written in binary so the shape reads off the source. The tests pin
the SHAPE - a dotted line has gaps, a long dash runs longer than a short one, the phase carries -
rather than exact pixels, because exact pixels would only test the choice against itself.

### 5. Raster writing modes — DONE 2026-08-17

    ESC / 0 d   overlay      set dots on
    ESC / 1 d   erase        set dots off
    ESC / 2 d   complement   complement dots

The manual flags these itself: "NOTE: These sequences are not part of the 4010/4014 protocol." They
are DEC's addition, and the restrictions section says why they exist — a real 4014 could draw
WITHOUT storing, refreshing to keep the image visible, and "the VT300 can simulate write-through
functions by using raster writing modes".

**The parser splits them, and it is right to.** DEC prints four bytes (1/11 2/15 3/0 6/4), but that
is not a conformant escape sequence: `/` is an intermediate and `0` is already a valid FINAL, so
ECMA-48 ends the sequence at the digit and leaves the `d` as an ordinary character. The parser
recognises structure and never interprets, so the oddity is handled in the one terminal that has
it — the mode is set on `ESC / 0|1|2` and exactly one following `d` is swallowed. A host that sent
the sequence without its trailing byte cannot lose a real `d` later.

**Where the mode lives.** `IGraphicsSurface` gained a `WritingMode` property rather than another
parameter on every draw call: a writing mode applies to everything drawn while it is in force, and
threading it through would change signatures that no other protocol needs. `SetPixel` is the one
place that honours it, so lines, circles and points all inherit it; the bulk fills deliberately do
not, because they belong to protocols with no writing modes and a span fill cannot express a
complement anyway.

### 6. What `ESC FF` is supposed to reset — DONE 2026-08-17

The manual: "Selecting alpha mode erases the screen, moves the current position to the upper-left
corner, activates margin 1, and clears the bypass condition. Selecting alpha mode also resets the
pattern register and intensity."

**All five now.** The erase and the home, bypass cleared, the vector pattern back to solid, and —
now that margins and writing modes exist — margin 1 and overlay writing. The comment left in
`EraseScreen` warned that these had to land here when they arrived so `ESC FF` could not quietly
leave state behind; that is what happened.

### 7. Margins — DONE 2026-08-17

Two-column writing, and the manual gives it step by step:

> "Margin 1 is at the left edge of the display area. Margin 2 is at the center of each row in the
> display area... The active margin automatically switches after one of the following events: the
> terminal fills the last row for the currently active margin; the terminal receives a line feed on
> the last row of the display. The terminal then wraps characters around to the top row of the
> display, at the new margin."

A storage tube cannot scroll, so this is what a 4014 does *instead* of scrolling: fill the screen,
start again at the top in the right-hand column "overstriking any characters already displayed",
fill that, and go back to the left. One-column writing is not a separate mode — "if you want
one-column writing, then you must clear the screen before characters wrap around to margin 2" — so
there is nothing to switch off, and a host that erases often never sees margin 2.

**It needed `ResolveDeferredWrap` first.** The snap to the centre column reads the cursor, and a
character that fills the last column leaves the cursor sitting there with the Last Column Flag
armed rather than on the next row. Snapping before the deferred wrap was resolved did nothing at
all; the test caught it.

**It also moved an existing test's goalposts, correctly.** `LinefeedStopsAtTheBottomOfTheScreen`
asserted the cursor simply stops at the bottom row. That is still true for every other terminal and
is now false for a 4014, whose line feed at the bottom has somewhere else to go. The invariant the
test was really written for — the cursor must not run off the screen — is what it now checks there.

## Nothing is left

Every item this document found is implemented. The chapter is walked, and what remains for
Tektronix mode is judgement rather than code — whether a 4014 stream looks right on real glass.

## How it gets judged

The three vendored gnuplot streams in `tests\RetroTerm.Tests\Conformance\tektronix\` stay the
regression oracle. None of them exercises anything in the missing list, which is precisely why the
list needed a manual to find: a corpus can only ever prove the parts it uses.
